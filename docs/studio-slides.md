# EvoAgentX Studio 介绍 PPT：逐页内容说明

> 用途：向团队或相关方介绍 EvoAgentX Studio。
> 结构：动机 → 功能 → 相比纯写代码的优势。
> 建议 14 页，讲 20–25 分钟。下面每一页都写明：**这一页要讲清楚什么**、**页面内容**、**建议的版式或图**、**讲稿要点**。
> 文中带 `[ ]` 的地方需要你补上实际数字或截图。

## 第 1 页 · 封面

- **要讲清楚：** 这是什么东西，一句话。
- **页面内容：**
  - 标题：EvoAgentX Studio
  - 副标题：从数据到评估、再到自动优化的 Agent 工作流平台
  - 署名、日期
- **版式：** 左侧大标题。右侧放一张画布截图，最好是正在运行、高亮当前节点、边上显示数据流向的那种。
- **讲稿要点：** 先说清楚这是一个通用平台，信用风险监控只是跑在上面的一个项目。

## 第 2 页 · Motivation (1)：纯写代码做 Agent 工作流的痛点

- **要讲清楚：** 为什么需要这个平台。痛点都来自真实开发过程，不是泛泛而谈。
- **页面内容**（每条一行，配一个图标）：
  1. **迭代慢：** 改一个 prompt、换一个节点顺序，就要改代码、重跑脚本、翻日志。
  2. **执行过程看不见：** 多节点、多记录、带记忆的流程，出了问题很难知道卡在哪一步、哪条数据、哪个节点。
  3. **数据、记忆、评估各自为政：** 数据加载、记忆读写、评估脚本、优化实验散落在不同脚本里，彼此不一致。
  4. **跑大批量不可控：** 停不下来，失败了不会自动重试，中途挂掉没法续跑，token 花了多少也要事后才知道。
  5. **非工程师参与不了：** 懂业务的人改不了 prompt，也看不懂结果。
- **版式：** 左边 5 条痛点，右边一张"纯代码时代"的示意图，比如一堆脚本和日志文件。
- **讲稿要点：** 挑 1–2 条讲真实经历，比如"跑到一半想停，只能杀进程；再跑一遍记忆就乱了"。

---

## 第 3 页 · Motivation (2)：我们要的是什么

- **要讲清楚：** 目标。痛点反过来，就是平台的设计原则。
- **页面内容**（4 个卡片）：
  - **看得见：** 流程画在画布上，运行时能看到正在跑哪个节点、数据怎么流动、每个节点进行到哪一步。
  - **管得住：** 能停、能重试、能续跑，token 用量和费用实时显示。
  - **闭环：** 数据 → 运行 → 评估 → 自动优化 prompt → 验证，全在一个地方完成。
  - **通用、可扩展：** 不绑定某个业务；数据集、工具、评估都能用自己的 Python 代码接进来。
- **版式：** 2×2 卡片。
- **讲稿要点：** 强调"平台是通用的"。业务字段（公司、日期等）不写死在平台里，由各个项目自己的插件和数据集提供。

---

## 第 4 页 · 整体架构

- **要讲清楚：** 系统由哪几块组成，边界在哪里。
- **页面内容：**
  - **Frontend：** 画布编辑器、运行动画、Records / Memory / Usage 等面板、Evaluation & Evolve 面板、Chat。
  - **Backend：** 工作流引擎（按节点分批执行）、数据加载、记忆、评估和 Evolve、运行记录。
  - **llm 包：** 独立的模型接入层，按统一接口（llm-v12）对接不同供应商。本地测试用 DeepSeek，生产用 SafeChain；换供应商不用改平台代码。
  - **studio-data：** 所有用户数据（workflow、运行、batch、记忆、数据集）和代码分开存放。
  - **项目插件：** 每个项目自带数据源、预设模板和工具包（比如 credit_risk）。
- **版式：** 分层架构图，前端 → 后端 → llm 包 / studio-data，旁边挂"项目插件"。
- **讲稿要点：** llm 包独立出来的意义：模型供应商的差异（认证、批量接口、用量统计）全部挡在平台外面。

---

## 第 5 页 · Functions (1)：搭建工作流

- **要讲清楚：** 怎么把一个流程搭起来。
- **页面内容：**
  - **画布：** 拖放节点、连线、字段映射；左侧是节点库和模板。
  - **节点类型：** LLM Task、Summarizer、Report Writer、Chat Agent（Deep Agents，可以调用工具）、Shared memory、Input（数据源）。
  - **工具：** 可以是一段完整代码、一个类，或上传一个包（支持 import），配置参数从代码里自动读出来。
  - **Chat 助手：** 用自然语言描述需求，它帮你搭流程、改节点、解释运行结果。
  - **Skills：** 可复用的常驻指令，注入到节点的 system prompt 里。
- **版式：** 左侧画布截图（标注节点库、画布、Inspector、Chat 四个区域），右侧列要点。
- **讲稿要点：** 工具和 Agent 的接入不依赖模型供应商有没有原生 function calling。平台用文本协议实现工具调用，所以 SafeChain 也能用。

---

## 第 6 页 · Functions (2)：数据接入（DataLoader）

- **要讲清楚：** 数据怎么进来，尤其是按时间分批的数据。
- **页面内容：**
  - 用 PyTorch Dataset 代码定义数据集：`build_dataset(resource, …)`，带类型的参数会自动生成表单。
  - 可以预览，看到输出字段和样例记录。
  - **按批读取：** 数据流式按批读入，每批就是一个时间窗口，可以按日、周、月分组。
  - 声明"轨迹"（按实体分组，比如 company），同一实体的记录严格按时间顺序执行。
  - 预处理工具、共享参考数据（每条记录都能看到的列表）。
- **版式：** 左边一段 Dataset 代码截图，右边是生成的参数表单和预览表格。
- **讲稿要点：** 数据加载代码跑在隔离的子进程里（比如用 spaCy 做 PII 脱敏），和平台自身的依赖互不冲突。

---

## 第 7 页 · Functions (3)：记忆（Memory）

- **要讲清楚：** Agent 怎么"记住"历史，并且不乱。
- **页面内容：**
  - **table 记忆：** 按实体、按日期记录，比如每家公司每个时间点一条；检索时只取目标日期之前的记录，防止用到未来信息。
  - **recall 记忆：** 向量检索（bge-small），做语义召回。
  - **读写规则：** 一个节点可以读其他节点的记忆；写哪些字段、什么时候写（成功时、失败时）都可以配置。
  - **管理：** 记忆页可以浏览和搜索；备份和重置是两个独立操作。
  - **性能：** 同一批记录共用一份打开的记忆库，统一保存一次。内部实测：32 条写入 2000 条的库，127 秒降到 4 秒。
- **版式：** 左边一张时间轴示意图，展示每家公司的记忆随时间积累、检索只看过去；右边列要点。
- **讲稿要点：** 时间序列场景最怕"偷看未来"。table 记忆按日期截断，是这种场景能做对的关键。

---

## 第 8 页 · Functions (4)：运行与可观测

- **要讲清楚：** 大批量怎么跑，怎么看，怎么控制。
- **页面内容：**
  - **按节点执行：** 一个 DataLoader 批次的所有记录先一起跑完节点 A，再一起跑节点 B……批次之间按顺序执行，前一批写入的记忆，后一批一定能读到。
  - **实时动画：** 高亮当前节点、显示输入输出字段怎么流动；每个节点显示已完成的记录数。
  - **可控：**
    - Stop 立即生效，包括正在等模型返回的调用和正在写记忆的操作。
    - 临时错误（超时、限流）自动重试。
    - 中断后可以续跑（Resume）。
  - **可追溯：** 运行记录写在 `runs/<开始时间>/batch_<n>/nodes/<节点>.jsonl`，每个节点收到什么输入、产出什么输出都有。
  - **Usage 页：** 实时显示 token 和费用，可以按节点、按记录拆开看。
  - 支持供应商的原生批量接口：一个节点的一个批次只发一次请求。
- **版式：** 一张运行中的画布截图，加上 Usage 页截图，再加一个 runs 目录树。
- **讲稿要点：** 讲一个具体场景，比如"凌晨跑 4000 条，第二天一早能看到每个节点花了多少 token，哪些记录因为超时重试过"。

---

## 第 9 页 · Functions (5)：评估（Evaluation）

- **要讲清楚：** 怎么衡量一个工作流好不好。
- **页面内容：**
  - 评估就是你自己写的 Python 代码：`evaluate(records, …)` 或 `build_evaluator(…)`，参数从代码里自动读出来生成表单。
  - 在 New run → Evaluation 里直接粘贴或上传代码；草稿会自动保存。
  - 数据可以是已保存的 batch 或运行（不用重跑），也可以用画布 Input 重跑一遍。
  - 可以接一份单独的标注数据，由代码决定怎么和运行结果对上。
  - 报告跟着这次评估保存；如果评估的是某个 batch，也存在那个 batch 上，任何时候都能回看。
- **版式：** 左边一段评估代码，右边一份报告截图（指标、覆盖率、每条记录的得分）。
- **讲稿要点：** 平台不内置任何业务指标。"好不好"由每个项目自己用代码定义，所以适用于任何任务。

---

## 第 10 页 · Functions (6)：自动优化（Evolve）

- **要讲清楚：** 怎么让工作流自己变好，而且结果可信。
- **页面内容：**
  - **Evolve 接着一次评估进行：** 用那次评估的代码当目标，从它的报告里选一个指标来优化。
  - **dev/val 切分：** 按实体（比如公司）或任意字段切分；可以把最新的时间段留作 val。每轮用 dev 提出和挑选 prompt；val 只在最后打一次分，不参与任何决定。
  - **每轮从空记忆开始：** 基线和每一轮候选都用独立的记忆，从头重跑整条时间线，互不干扰，也不碰真实 workflow 的记忆。
  - **省 token：** 如果评估本身就是用画布 Input 重跑的，而且之后数据和 workflow 都没变，Evolve 直接复用那次结果当基线。
  - **结果：** 显示 prompt 改了什么、dev 上的前后分数、val 上的前后分数（没提升会提示"可能不能推广"）；可以应用到当前 workflow（会自动留一份备份）或另存为新 workflow。
- **版式：** 流程图：评估 → 切分 dev/val → 基线 → 提出候选 → 在 dev 上重跑并打分 → 选出最好的 → 在 val 上验证 → 应用。
- **讲稿要点：** 为什么要留出 val：用来提 prompt 的数据和用来选 prompt 的数据是同一份，分数会偏乐观；独立的 val 才能说明是真的变好了。

## 第 11 页 · Advantages over pure coding (1)：对比表

- **要讲清楚：** 核心结论页，逐项对比。
- **页面内容（表格）：**

| 方面 | 纯写代码 | EvoAgentX Studio |
|---|---|---|
| 搭建和修改流程 | 改代码、重跑脚本 | 画布上直接改，Chat 帮你改 |
| 看执行过程 | 翻日志、加 print | 实时动画、每个节点的进度、每个节点的输入输出 |
| 大批量运行 | 自己写并发、重试、续跑 | 内置按节点分批、自动重试、Stop、Resume |
| 记忆和时间顺序 | 自己保证不偷看未来、不写乱 | 按实体和日期隔离，批次顺序由平台保证 |
| 成本 | 事后对账 | Usage 页实时显示，按节点、按记录拆分 |
| 评估 | 每次单独写脚本 | 代码评估，报告跟着结果保存 |
| 优化 prompt | 手工试 | Evolve 自动优化，dev/val 验证，每轮记忆隔离 |
| 换模型供应商 | 改业务代码 | 只换 llm 包，接口不变 |
| 协作 | 只有工程师能改 | 懂业务的人也能看、能改、能评估 |

- **版式：** 全页表格，Studio 那一列用强调色。
- **讲稿要点：** 不用每行都讲，挑 3 行讲具体例子。

## 第 12 页 · Advantages over pure coding (2)：不是低代码的妥协

- **要讲清楚：** 回应"平台会不会限制灵活性"。
- **页面内容：**
  - **关键的地方仍然写代码：** 数据集、工具、评估都是完整的 Python，可以 import 任何库、写类、上传一整个包。
  - **平台负责繁琐的工程部分：** 并发、顺序、记忆一致性、Stop 和重试、落盘、恢复、用量统计。
  - **可复现：** 每次运行都保存当时的 workflow 快照和完整输入输出；Evolve 的基线、切分、种子全部有记录。
  - **安全隔离：** 用户代码跑在单独的进程里；Evolve 的实验不碰真实数据和记忆。
- **版式：** 左右两栏：左边"你写的"（业务逻辑），右边"平台做的"（工程保障）。
- **讲稿要点：** 一句话总结：把工程师的时间从搭脚手架移到业务逻辑上。
