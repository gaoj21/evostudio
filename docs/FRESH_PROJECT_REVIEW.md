# 从零创建通用项目：代码审查

日期：2026-09-14。范围：Project/Task、输入、连线、执行、结果评估、Evolve、资源复用及导入迁移。
本次只审查和隔离复现，没有修改业务实现，没有运行付费模型。`backend/llm/` 和 `backend/evoagentx/models/` 未修改。

## 修复进度（2026-09-14）

已修复：导入图配置与显式连线语义保留、缺失依赖报告、历史结果的领域无关默认指标、优化证据携带通用输入、数据集引用检查与独立解绑、真实列类型及 Input 局部类型转换。

画布撤销新增：即时撤销未等满 350ms 的编辑、流程级配置、独立 Chat 节点配置/连线/删除恢复；Chat 定义恢复会写回服务端，保留会话与检查点，有会话运行时拒绝恢复。节点选择及测量变化不再产生有效历史步骤。

原生批量在执行前检查工具参数能力，仍不修改公司维护的 LLM 及框架 models 目录。

仍属功能边界：多输入目前是一条主数据流加共享参考表；本轮未新增双逐行表 Join、原生 Excel 读取或公司 API 内部实现。导入不会搬运私有 Memory 内容和数据集文件，缺失或越作用域的依赖会明确列出，需重新绑定。

后文保留审查时的复现记录，用于理解修复原因。

## 结论

当前系统已有通用执行骨架，但资源管理、导入恢复、评估和优化仍有依赖既有 credit-risk 使用方式的假设。新项目最明显的障碍发生在“换一种输入”“复用/迁移”“对自己的结果评估和优化”，并非仅仅按钮或面板问题。

## 已确认的问题

### 1. P1：导入改变 Workflow 的语义，并丢失配置

位置：`backend/features/workspace/project_import.py:165`。

导入时重新拼装保存对象，仅带 name、goal、output_dir、tasks、edges，遗漏 flow_version、preprocess、memory_resources、memory_positions。

隔离复现：导入一个 flow_version=2、配置了预处理及共享 Memory 布局、含显式 order-only 边的 graph.json。
结果：预处理变为 null，Memory 资源与布局为空；因为版本丢失，加载又执行旧版迁移，同名字段的 order-only 边被改成数据映射。

影响：把已有流程作为新项目起点时，看起来导入成功，实际执行逻辑可能已经变化。

修复方向：建立完整的图配置序列化合同；保留版本与显式边语义；对新图 ID 相关的 Memory、dataset、工具引用明确重绑定或报缺失。以“导出→导入后执行计划一致”为验收标准，而非只检查节点数量。

### 2. P1：通用任务的已保存结果默认使用 credit_risk 指标

位置：`frontend/src/features/evaluation/EvolveForm.jsx:71`；`backend/features/evaluation/saved_result_evolution.py:72`。

所有 saved_batch / saved_run 默认被选为 credit_risk，与任务类型和标签无关。

隔离复现：一条普通分类记录，预测 yes、标签 yes。使用 credit_risk 得到 scored=0、score=null；切换 exact_match 得到 scored=1、score=1.0。

影响：从零做分类、抽取或计算任务，正常结果在默认评估操作下仍无法得到有效分数。手动选择适当指标可以绕过，因此不是完全不支持通用评估。

修复方向：默认由用户确认标签字段、预测字段和指标，或者从任务评估配置加载；运行前显示可评分数量。credit_risk 只在明确选择该领域任务时启用。

### 3. P1：基于历史结果 Evolve 时没有保留通用输入证据

位置：`backend/features/evaluation/saved_result_evolution.py:109`。

发给优化模型的记录只从输入取 company、as_of，其他输入全部省略；虽然保留预测、标签和所选节点输出，但无法保证包含原始问题或材料。

隔离复现：输入 customer_text="critical evidence"，生成的优化证据里仅有 company=null、as_of=null，不包含 customer_text。

影响：在客服、合同抽取、商品分类等新项目中，优化器可能看到答案与分数，却看不到产生它们的原始材料，无法可靠分析错误原因。

修复方向：使用通用 inputs 与各节点实际接收的输入，按预算裁剪并标记截断；领域摘要作为可选扩展，而不是唯一输入。

### 4. P1：全局数据集删除缺少使用关系检查

位置：`backend/features/data/user_datasets.py:190`；列表也是全局范围。

删除直接移除数据集文件，不查询引用它的 Workflow。前端只清空当前 Input 的 dataset_id，其他 Task 保留悬空引用。

隔离验证：删除前 records(config) 正常返回；删除后同一配置立即报 Dataset no longer exists。引用检查缺失由删除路径确认。

影响：新项目复用旧项目上传的数据后，任意一处删除会让其他项目在下次运行时失败。

修复方向：区分“从当前 Input 解绑”与“删除共享资源”；列出引用 Task，默认阻止删除使用中的资源，或要求显式选择处理方式。资源的适用范围也应在 UI 标明。

### 5. P2：输入字段显示的类型与实际数据没有一致合同

位置：`frontend/src/features/data/DatasetInput.jsx:34`；`backend/features/data/user_datasets.py:59`、`records()`。

JSON 可保留数字、数组、对象；但 DatasetInput 将所有逐行输出声明成 str。CSV 的数字也仍是字符串，没有列类型转换步骤。

验证：JSON 的 amount=12、tags=["a"] 在解析后分别为 int/list，前端对应声明仍为 str。不能据此断言所有运行都会失败：LLM 路径会转成提示文本，工具路径接收原值。问题在于同一连线上的类型声明不可靠，计算工具最容易暴露差异。

修复方向：导入时提供列类型推断与用户覆盖、缺失值策略；连线应呈现真实类型，类型转换应显式发生，运行前做样本预检。

## 已有能力的边界，而非代码故障

### 6. 多输入仍限定为“一条逐行流 + 多份共享参考”

位置：`backend/features/data/input_composition.py:17`。

该模式能覆盖新闻 + obligor list，但两份逐行表不能直接按主键 join，也不能选择 zip、union 或笛卡尔积。连接两份普通 CSV 后会要求其中一份改为共享参考。

建议：让 Input composition 显式选择主数据与参考数据；需要关联时增加独立 Join/Filter/Aggregate 工具节点。不要将“共享整表”当作所有多输入任务的默认答案。

### 7. 文件与原生批量能力需要更早展示适用范围

输入目前支持 CSV/TSV/JSON/JSONL，Excel 需要先导出为 CSV。不能把现有导入能力描述成原生 Excel 工作流。

SafeChain 文本批量接口可只接收 provider、inputs；Deep Agents 会附带工具 schema 等选项。外层校验目前先确认 batch 可调用，带工具时才检查选项签名，因此文本可跑不代表带工具的新项目也可跑。公司实现的能力仍需在公司环境验证。

建议：执行前按实际节点检查能力，并在计划里显示未满足条件。两个冻结目录之外就可以实现这层检查。

## 推荐实施顺序

1. 修复导入恢复合同，防止无声改变执行语义。
2. 将评估默认指标和 Evolve 证据改为领域无关。
3. 补资源引用关系、解绑/删除语义、缺失依赖提示。
4. 统一输入 Schema、类型转换和显式字段映射。
5. 扩展多输入组合能力，并完善执行前检查。

避免继续为每个项目增加特殊默认值。通用层应管理图、输入输出合同、依赖资源、执行计划、评估配置；credit-risk 的字段、数据集与指标应通过项目配置提供。

## 验收用的新项目场景

- CSV 工单分类：text → classify → category；标签在独立评估配置中，能复用已有结果计算 accuracy。
- JSON 数值计算：数字、数组、空值 → 确定性工具 → 结果，确认类型无需猜测。
- 双表关联：订单 + 客户表 → 按 customer_id 关联 → 汇总，明确当前尚需实现 Join 能力。
- 带 Memory 的通用 Agent：同一会话持续交互、独立会话隔离，保存重开后资源连接一致。
- 新环境导入：不依赖原机器的运行历史；所有配置要么恢复，要么列出待补依赖；不得静默改边。

本次隔离复现只覆盖上述明确列出的情形，不等同于真实公司 API、所有浏览器交互或所有任务类型的端到端验收。
